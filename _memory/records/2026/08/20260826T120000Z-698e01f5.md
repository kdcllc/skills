## Problem

Phase 7 `ship-pr` assumed GitHub (`gh`, hardcoded `origin`). Non-GitHub forges had no delivery path; setup told users to delete Phase 7 from ORCHESTRATION — a fan-out across many template references that shipped incoherent installs (including Azure DevOps field reports).

## Outcome

Shipped kit **v0.22.0** (release commit `bfb41bd`; dogfood branch commit `1841973`). Runtime **forge detection** in canonical `ship-pr` (`github` / `azuredevops` / `gitlab` / `none`) from remote URL with documented precedence, overridable via manifest `options.forge` (+ optional `options.forgeHost`). Branches: `gh` regression-identical to prior skill, `az repos pr`, `glab mr`, and `none` draft-plus-hand-over with **no create call**. Base branch via `git ls-remote --symref` on the PR-target remote with three stop-and-ask ambiguity cases. Setup question 7 records forge; re-run refreshes detection. **Phase 7 is never deleted** — language sweep removes delete-Phase-7 instructions. Guard `tests/templates/forge-adapter.sh`. User skipped Phases 5–6 by override; eight tasks PASS cycle 1. PR create hand-over when `gh` token lacked repo access.

## Key decisions

- Single runtime forge-aware skill (approach A), not emit-time forge variants or new tokens.
- PR-target remote vs push remote stay distinct (fork workflows preserved).
- On-prem Azure DevOps Server → hand-over only (no REST fallback this goal).

## Pitfalls / lessons

- SSH-alias remotes may be pattern-undetectable — manifest override is the designed escape hatch.
