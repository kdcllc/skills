## Question

How to deliver Phase 7 `ship-pr` on non-GitHub forges without leaving emitted kits incoherent when Phase 7 is deleted?

## Load-bearing findings

- Azure DevOps cloud: `az repos pr create` / list / update; extension `azure-devops`; PAT vs `az login` footgun; no CLI for ADO Server on-prem.
- No-forge fallback: draft, push, hand over PR-creation URL or REST with server-specific api-version—preserves human-approval invariant.
- URL-based forge detect for GitHub/Azure/GitLab.com; self-hosted needs explicit override in manifest (not git config writes).
- Multi-remote precedence should mirror `gh` (upstream → github → origin) with explicit override; default branch via `git ls-remote --symref`.
- Claude-only installs cannot natively cross-family rotate; path-scoped rules do not reliably reach fresh subagents on any harness—put critical rules in always-loaded root files or context packages.
- Prose emission must avoid shell heredoc/sed corruption; use UTF-8 safe token substitution.

## Decisions taken

- Forge override in `orchestration-kit.manifest.json` options, respecting ship-pr guardrail against writing git config.
- Single-family degraded mode: external-feedback framing + reflection + earlier escalation; effort-escalation as cross-family substitute is unproven.

## Open questions

- `az repos pr list` branch name forms; legacy SSH remotes; whether effort escalation reduces same-family blind spots.
