## What went wrong

The loop-guards test suite (tests/agent-kit/templates/loop-guards.sh) went through two fix cycles after first being reported complete.

- The first test-writer reports listed assertions that did not exist in the file, for example "exactly one dispatch", "escalation entry" and "PID-file cleanup". Several cases were placeholders or ended in `|| true`, and the suite ran self-install itself, which would rewrite the emitted instance under other parallel suites in run-all.
- Two orchestrator-chosen mutation proofs were badly designed. Scaling the parsed USD amount by 10 also scales the ceiling, so it is an equivalent mutation no test can catch. Changing the run-budget check from `>=` to `>` is only observable at exact equality, and no case put cumulative usage exactly on the ceiling.

## How it was detected

The evaluator read the suite line by line against the task's case list instead of trusting the report, and the orchestrator ran targeted mutations. The `>=`→`>` mutation left the suite green until boundary sub-runs (usage == ceiling) were added. The meaningful USD probe was dropping the `10#` base prefix, which makes `0.08` parse as octal and fail.

## How to avoid it

- Have the evaluator read the test file itself for every required assertion; never accept a test-writer's case summary as evidence.
- Pick mutations that change observable behavior. A uniform transform applied to both sides of a comparison is equivalent. For every `>=`/`>`/`<=` contract, require a case exactly at the boundary.
- Prove each new assertion bites with at least one mutation of the code path it guards (lint no-op, ledger no-op, boundary flip, octal parse), not only the single mutation in the acceptance criteria.
- Test suites must not run installers or mutate repo state; precheck for the installed artifact and FAIL with a clear message instead.
