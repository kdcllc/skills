Pitfall: documentation tasks given to light-tier implementers produced confident but false claims, and every docs task in goal agent-kit-1-0-docs needed one or two fix cycles.

What went wrong:
- Bulk regex rewrites of research studies deleted a finding, garbled a story id ("STORY-010 (v0.11.0)" became "STORY (1.0.0)"), and wrote false history ("a 1.0.0 install field report" for a release that never existed).
- New Mermaid diagrams had wrong actors (the memory CLI running check on itself; evaluators writing spawn reports), wrong order (backlog update after merge), and missing branches (rung 4 with no PASS path).
- One fix introduced a new false claim: "_loop/ is gitignored on every emit". emit.sh gitignores only _kit/ and three _memory/ paths; _loop/ is gitignored only in this repo's dogfood instance.
- A changelog merge attributed emitter behavior to the memory README and framed items against pre-release agent-kit instead of setup v0.30.0.
- A test speed-up cloned fixtures with `cp -al`. A later `>>` append wrote through the shared inode into the base fixture.

How it was caught: frontier evaluators spot-checked claims against canonical sources line by line, plus orchestrator evidence scripts (a link checker, a mermaid-cli render of every diagram with a negative test, per-task fence checks against a pre-task git-status snapshot, and comparison of each earlier task's evaluated patch with the current diff).

How to avoid it:
- In every docs context package, list the canonical sources and the known traps (gitignore set, fence recipients, rotation rule). Require a list of new claims with source file:line.
- Forbid bulk rewrites of studies; require hand edits and `git show HEAD:<file>` to restore text.
- Render-check every diagram (npx @mermaid-js/mermaid-cli) before evaluation.
- Snapshot git status and file hashes before each spawn so the write fence can be checked even when files were already modified.
- Never clone mutable fixtures with hard links.
