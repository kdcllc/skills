Pitfall: a mutation proof that only deletes a message line proves nothing about the dangerous direction of a destructive check.

What happened (agent-kit goal memory-prune): the first guard suite for `memory.sh prune` shipped in-suite mutations built with sed `/keep:uncommitted:/d` and similar. Deleting the `printf 'keep:uncommitted:%s'` line left `return 0` with an empty verdict, so the mutant still KEPT the folder (printed a blank reason). The suite caught it, but only because the message vanished; a real bug that turns a kept folder into `would-delete` was never exercised. The task evaluator flagged it; mutations were moved out of the suite (they also hard-coded exact source text, so a harmless refactor would fail the guard) and rewritten as `if <condition>; then` → `if false; then`, which makes the check fall through to `would-delete`. Those mutants failed cases 5/8/9 and 12a as intended.

How to avoid:
- For a destructive command, each mutant must flip a keep decision into a delete decision (or the reverse), not just remove output.
- Guard every mutant with an expected changed-line count and `bash -n`, run an unmodified control first, and assert the targeted FAIL lines.
- Keep mutation proofs out of the shipped suite unless they are robust to refactors; record them in the report.
- Assert exit codes in every case and make each case able to see its rule (e.g. put the missing id right before the `;` when testing substring id extraction).
