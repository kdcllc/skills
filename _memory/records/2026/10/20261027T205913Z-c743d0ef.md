Decision: `memory.sh prune` treats a record as durable only when its file is in `HEAD` AND, when the repo has a remote default branch, in that branch too (first resolvable of `refs/remotes/origin/HEAD`, `refs/remotes/origin/main`, `refs/remotes/origin/master`; local remote-tracking state only, never fetches). With none of those refs, `HEAD` alone decides.

Why: the original rule ("committed in HEAD") was unsafe. The ship-pr skill reads `_memory/work/goals/<goal>/orchestration-log.md` for every goal delivered on the PR branch to write the self-evaluated-gates section, and one PR can carry several goals (loop manual mode commits each story, then ships once). Prune runs at the next feature Phase 2, so a goal committed on the branch but not yet merged would lose its log before the PR was written or reviewed. Requiring the record on the remote default branch keeps folders until their PR merges.

Alternatives rejected: HEAD-only with the loss documented; HEAD-only but skip prune inside loop iterations; a one-run trash folder for undo (user chose outright deletion).

Consequences: folders stay until `origin/…` is fetched after merge (safe direction); repos without an `origin` default-branch ref fall back to HEAD-only and can prune a committed-but-unshipped goal early (documented in the README and memory protocol); new keep reason `keep:unmerged:<id>`.
