Pitfall: grep -F (or grep -qF) with a multi-line pattern does not check a contiguous block. grep treats each newline-separated line of the pattern as a separate alternative and succeeds when ANY single line matches anywhere in the file.

What happened (goal agent-kit-opt-in, tests/agent-kit/templates/opt-in.sh): the helper that asserted the ORCHESTRATION.md opt-in note "as a contiguous byte-exact block" was `grep -qF -- "$block" "$f"` with a six-line block. Lines 1 and 3-6 are identical across the four research x loop variants, so the check passed for any variant and for a garbled variant line. The suite ran 12/12 green and the test-writer reported no gaps.

How detected: the orchestrator ran its own mutation probes on scratch copies of the kit (EMIT_KIT / EMIT_SH overrides); appending text to one variant line left every case PASS. Reading the helper and a two-line demonstration (pattern "line one\nNOT PRESENT" matched a file containing only "line one") confirmed the cause.

Avoid it:
- For multi-line expectations use whole-content substring matching (content="$(cat "$f")"; [[ "$content" == *"$block"* ]]), cmp/diff against an exact heredoc, or an awk contiguous-line matcher.
- Related trap found in the same suite: reading an expected prefix through `read -r -d '' VAR <<'EOF'` strips trailing whitespace, so an assertion "starts exactly with '<prefix> '" silently loses its trailing space. Use a single-quoted literal for strings whose edge whitespace matters.
- Put this in test-writer packages up front and mutate one line of every multi-line expectation when gathering evidence.
