## What went wrong

Task 04 replaced the loop driver's per-line `grep` tamper scan with an awk program embedded in `_loop_tamper_reason_lines`. The program was written at column 0, so its `BEGIN { … }` block closed with a `}` at the start of a line. The repo-wide way to extract a shell function, `sed -n '/^name()/,/^}/p'`, stops at the first column-0 `}`. The task's own acceptance criteria (AC1, a forbidden-construct grep, and AC3, a count of per-line loops) used that extraction, as do several suites. So they inspected only the first half of the function while still printing passing results.

## How it was detected

The orchestrator's old-versus-new smoke test extracted the function with that `sed` range. The extracted file failed `bash -n` with "unexpected EOF while looking for matching `''", and `tail -2` of the range showed it ending inside the awk program.

## How to avoid it

- Indent every line of an embedded awk (or other here-text) program so that no line inside a shell function starts with `}` (leading whitespace means nothing in awk).
- After editing a function that contains embedded programs, check that `sed -n '/^name()/,/^}/p' file | tail -1` prints the function's own closing brace.
- When a criterion inspects a function by extracting it, compare the extracted line count with the function's real span.
