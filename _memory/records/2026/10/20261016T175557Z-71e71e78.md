Pitfall: launching a subagent in the same parallel tool batch as the shell command that writes its context package means the subagent can start before its inputs exist.

What happened (agent-kit goal orchestration-evidence-collector): to save a round trip, the orchestrator issued one shell call (write `spawns/22-context.md` and `23-context.md`, capture guard evidence, log the spawns) and two evaluator Task calls in the same batch. The shell call took ~36 s; both evaluators started immediately, found no context file and a half-written evidence file, and returned NEEDS FIXES verdicts about missing inputs. Two wasted evaluator runs, two invalid ledger entries to close, and a re-dispatch under new spawn numbers.

How detected: both evaluators reported "File not found" for their context package and an evidence file that ended mid-section.

Avoid it: write and verify every input a subagent will read (context package, evidence files, ledger SPAWN line) in one tool call, check the files exist (`ls`), and only then launch the subagent in the next call. Parallelize subagents with each other, never with the commands that prepare them. The same applies to the evaluator-in-flight rule: nothing an evaluator is told to read may change while it runs.
