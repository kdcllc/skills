Open follow-ups after goal memory-store-d-backfill (agent-kit memory store Release D, unreleased). None blocks the release; the final audit was APPROVED with notes (4/5).

Product and docs:
1. The README's closed-goal rule 3c (`--only`) does not document the fallback. When the log has no valid `### <ts>` heading at all, the id falls back to `19700101T000000Z`.
2. Performance: backfill runs `add` as a separate process for each record, spawns `printf | grep` for each log line, and does a full frontmatter scan of all records for each goal. It will be slow on large stores and under Git Bash on Windows.
3. `--plan` always reports resolved escalations as `would-add`, even after they were applied; only `--apply` reports `duplicate`. This is documented, but `--plan` could detect it.
4. `resolved: YYYY-MM-DD` dates are not checked as real calendar dates.
5. A research report whose `**Date**:` line ends in CRLF falls back to the 1970 id; strip CR in that parse.

Tests:
6. Older mutation cases in tests/agent-kit/templates/memory-backfill.sh predate the `expect_changed_lines` argument. Add it so each mutation is proven to edit exactly one line.

Process and kit (carried from Release C, still open):
7. The emitted Cursor evaluator has `readonly: true` while its body requires running commands before scoring (pitfall 135a26e9). Release D's re-audit again relied on orchestrator-run evidence.
8. The transcript back-fill runbook has no native path for Codex-only installs. They run `capture` and distill from a Claude Code, Cursor or Copilot session.
