Decision: agent-kit bumps its version inside the PR that ships the release; `scripts/release-skill.sh agent-kit X.Y.Z` runs on master after the merge and, because X.Y.Z is already the recorded version, only validates and tags.

Why: besides `metadata.version` in skills/agent-kit/SKILL.md and the CHANGELOG heading (the only two files the release script edits), the kit version is encoded in tracked files the suite asserts: the `Kit version: **X.Y.Z**` line in skills/agent-kit/README.md (cursor-isolation.sh, forge-adapter.sh, escalation-ladder.sh, loop harness) and every emit golden (`kitVersion` in orchestration-kit.manifest.json.golden, `kit X.Y.Z` in emit.stdout.golden). A script-only bump on master leaves those stale, so the tagged commit fails run-all.sh and the README advertises the old version. Install pins (`#agent-kit/vX.Y.Z` in the README and docs/agent-kit/guide/getting-started.md) also drift.

Alternative rejected: bump on master with the release script, then fix README and goldens in a follow-up commit — the tag would point at a red commit.

Procedure (documented in docs/agent-kit/guide/contributing.md § Version and releases, with pointers in CONTRIBUTING.md and AGENTS.md): in the release PR set metadata.version, insert `## [X.Y.Z] - date` under an empty `## [Unreleased]`, update the README version line and install pins, run `emit-golden.sh --update` (expect only kitVersion / `kit X.Y.Z` lines beyond the PR's template changes), then validate-skills + run-all. Precedent: 1.1.0 (#3) and 1.1.1 (#4).
