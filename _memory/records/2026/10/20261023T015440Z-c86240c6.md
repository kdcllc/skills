## What went wrong

The loop driver's test-path classifier began with `local path="$1" base="${path##*/}"`. Bash expands every argument of a `local` (or `declare`, `export`, `readonly`) command before assigning any of them, so `${path##*/}` read the caller's `path` variable through dynamic scope, not `$1`. The tamper scan's rename/copy branch called the classifier before assigning its own `path`, so under the driver's `set -u` the first rename in a commit raised `path: unbound variable`. The scan ran inside a process substitution (`done < <(fn …)`), so the abort was silent: no signals, no error, exit status unchanged. A rename that sorted first could therefore hide every later tamper signal in the commit. When `path` happened to be set from an earlier entry, the basename rules silently classified the wrong file.

## How it was detected

An orchestrator smoke run through the real driver showed rename cases producing no signal, and three "pure rename, no signal" true negatives were passing only because the scan had aborted. Calling the function directly under `set -u` printed the unbound-variable error. The implementer's own smoke had claimed success because it ran without `set -u` / with `path` already set.

## How to avoid it

- Never reference a variable in the same `local`/`declare` command that assigns it; split into `local a="$1" b` then `b="${a##*/}"`.
- Smoke-test driver functions through the driver itself (or under `set -euo pipefail`), never by sourcing them into a lenient shell.
- Treat "no signal" true negatives as suspect until a true positive on the same code path has been seen; a crashed subshell looks exactly like a clean result.
- Process substitutions hide `set -e`/`set -u` aborts; check that their consumer can tell "no output" from "died".
