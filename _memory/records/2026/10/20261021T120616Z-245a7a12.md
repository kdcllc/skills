## Decision

Unattended Codex loop slots use `LOOP_CLI="codex exec --sandbox danger-full-access"`, documented as safe only inside an external container or VM sandbox. The guide states that the general SAFETY note (worktree or container) still applies to every loop run, and that for danger-full-access specifically a plain git worktree is not enough on its own: it gives no filesystem, network or credential isolation. Driver `# SAFETY:` headers and the guide's SAFETY line stay unchanged.

## Alternatives considered

- `--sandbox workspace-write`: reportedly keeps .git (and a linked worktree's gitdir) read-only, so slots cannot commit and are retired after three no-commit reaps.
- workspace-write plus the undocumented `sandbox_workspace_write.writable_roots` override: undocumented and fragile in worktree mode.
- Changing the SAFETY wording everywhere to container/VM: larger scope; the user kept it to the Codex paragraph.

## Rationale

Loop iterations must commit inside the CLI session. The stricter wording is scoped to the flag that removes the CLI's own sandbox, so it doesn't contradict the general guidance for other CLIs.

## Consequences

The CLI defaults behind this (Codex exec sandbox default, workspace-write .git behavior) are unverified locally; Codex is not installed. Docs phrase them as "reportedly"/"may". Re-probe when Codex is available and record the facts in harness-matrix.md.
