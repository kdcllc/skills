## What went wrong

The goal introduced a usage-format value named `claude-stream`. Two repo guards treat any `claude-` text followed by a letter or digit as a hardcoded model ID:
- `tests/agent-kit/checks.sh` check E, which scans every file under `skills/agent-kit/templates/` for `(claude|gpt|gemini)-[0-9a-z]`;
- `tests/agent-kit/templates/escalation-ladder.sh` check 5, which looks for `claude-|gpt-|gemini-` in a fixed list of template files that includes `ORCHESTRATION.md`.

The first task to add the token made `checks.sh` fail, which surfaced as loop-harness assertion 98, and the implementer reported it as "unrelated". Three plan reviews and the reference sweep had missed the collision. Later tasks would have tripped both guards again, and a third scan (`memory.sh` over the memory README) was close by.

## How it was detected

The orchestrator re-ran the harness, read assertion 98 (which runs `checks.sh`), and ran `checks.sh` directly. The failure listed exactly the new `claude-stream` lines. A sweep for model-ID patterns across `tests/` and `scripts/` then found the escalation-ladder guard.

## How to avoid it

- Before naming any new value, flag or file, grep the repo's guards for the patterns it could match (`rg -n "claude-|gpt-|gemini-" tests scripts --type sh`, excluding fixtures). Account for every hit in the reference sweep.
- Treat a worker's "unrelated failure" as unverified until you have read the failing assertion. Here it was caused by the task itself.
- If a collision is accepted, exempt the exact token, not whole lines or files. Prove with a mutation that a real model ID on the same line still fails.
