Pitfall: in this repo, a second agent session that runs tests/agent-kit/run-all.sh self-installs the dogfood instance (.cursor/, .claude/, _kit/, orchestration-kit.manifest.json) from the working tree. If another goal is mid-Phase-4, the install picks up half-edited canonical files.

What went wrong (goal evaluator-gate-hardening, 2026-10-28): a separate Cursor session ran run-all.sh three times while this goal was in Phase 4.
- One install landed mid-edit of templates/tools/log-spawn.sh. _kit/log-spawn.sh then advertised the new keys subcommand in its header but had no keys code.
- The installed task-criteria and fix-cycles picked up the goal's new rules before the goal finished.

How it was detected:
- A task evaluator noticed the ignored instance held text that existed only in the in-progress edit.
- The orchestrator traced the writer with mtimes and ps. A run-all.sh process whose parent was the Cursor NodeService, not this session's terminal, had launched at the same minute as the writes.

How to avoid it:
- When two sessions share a branch, only one may run run-all.sh (or self-install) while the other is in Phase 4. Otherwise pass --no-install.
- If it happens anyway, log an accepted reinstall deviation, re-verify the instance against canonical (diff -q), and continue. The Phase 5 self-install makes it consistent again.
- Path-limited commits (git commit -- <paths>) kept the other session's uncommitted edits out of this goal's commits.
