Pitfall: a mutation probe can "prove" coverage vacuously — by crashing the code under test — and a case can be unable to fail because its input never reaches the code path it claims to cover.

What happened (goal agent-kit-opt-in, tests/agent-kit/templates/kit-guard.sh): AC2 asked for a probe that drops .codex/config.toml from kit-guard.sh's user-config exclusions. The test-writer deleted the line `EXCL_CODEX='.codex/config.toml'`; under `set -u` every check and hook call then aborted on the unbound variable, so the suite failed and the probe was reported as passing. A faithful mutation (removing `|"$EXCL_CODEX"` from the case pattern, keeping the assignment) left the suite green: no case emitted the codex harness, so .codex/config.toml was never in the manifest and the exclusion was never exercised. The same review found a JSON "decoy key" case whose decoy held the same kit path as the real key (so a wrong-key bug could not flip deny to allow) and an AGENT_KIT_GUARD=0 check run on a clean root (where ignoring the variable is undetectable). The test-writer had also embedded the probes in the committed suite by re-running the suite against kit copies with the emit cache off, tripling its run time (77 s -> 263 s) in every run-all.

How detected: the task evaluator read the probe mechanics against the tool source; the orchestrator then ran exact-line faithful mutations for each exclusion, the deny exit code and the JSON unescape.

Avoid it:
- Mutate behavior, not definitions: change a branch, a value or an exit code; never delete a variable or function the code still references.
- For each case, first assert the precondition that makes it meaningful (e.g. the manifest lists the file whose exclusion is tested), then assert the outcome; make negative controls differ in exactly the dimension under test.
- Keep mutation probes as goal evidence (scratch kit copies via EMIT_KIT / EMIT_SH), not as committed suite cases.
