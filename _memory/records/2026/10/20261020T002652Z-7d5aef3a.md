Pitfall: a sourced test library that assigns a variable without `local` silently overwrites a caller's `local` variable of the same name (bash dynamic scoping), and the failure shows up only on some code paths — so a worker can honestly report a green run that does not reproduce.

What happened (agent-kit goal agent-kit-install-feedback): tests/agent-kit/lib/emit-cache.sh `_emit_cache_verify_entry` looped `while IFS= read -r line` without `local line`. That loop runs only on a cache hit. In the new install-feedback.sh guard, check (c) filled the cache, so checks (d), (e) and the second emit in (g) hit it; each had set `local line="<expected stderr line>"` before calling emit_cache_copy, and the loop left it empty, so they ran `grep -qxF '' …` and failed although emit exited 4 correctly. The test-writer reported 15/15 PASS; the orchestrator's plain default-cache re-run showed 3 FAIL.

How detected: orchestrator re-ran the guard independently before the task evaluation, then `bash -x` into a file showed `line='emit: blocked …'` set and later `grep -qxF ''`; the library's read loop was the only writer in between.

Avoid it:
- Declare every function-internal variable `local` in shared test libraries (fixed here: `local line` in _emit_cache_verify_entry, `local f` in _emit_cache_compute_key).
- In suites that source emit-cache.sh, give expected-output variables distinctive names (e.g. want_line) and assign them after cache calls.
- Always reproduce a worker's claimed pass with the plain command, default environment, and a cold cache before trusting it.
- Mutation proofs must start with an unmutated control run that passes and must assert the targeted FAIL line; a mutation that breaks syntax (e.g. deleting the only statement in a `then` branch) proves nothing.
