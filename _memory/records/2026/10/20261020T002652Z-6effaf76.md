Pitfall: a new emitter warning can break existing suites whose fixtures deliberately build the warned-about configuration to test something else, and an emitter task's regression AC list that names only a few suites will not catch it.

What happened (agent-kit goal agent-kit-install-feedback): task 01 added "warning: models.<h>.alt_family equals light; fix cycle 2 would not rotate models". tests/agent-kit/templates/model-currency.sh cases 4 and 7 (and bundle case 8) build answers with alt_family = frontier_alt_family = light (claude-sonnet-5-5) to exercise the arbiter-reuse warning and assert exactly one warning; they now got two. Task 01's AC7 listed emit-golden, emit-migrate, emit-determinism, forge-adapter and self-install --dry-run, but not model-currency, so task 01 passed its gate with the regression latent. It surfaced only when the orchestrator ran a broader guard set while gathering task 03 evidence; the suite passed at HEAD in a detached worktree, which proved attribution.

Avoid it:
- For any task that adds an emit warning, problem, or exit path, grep tests/agent-kit for suites that construct answers touching the same keys (e.g. `alt_family`, `frontier_alt_family`, `loop_chain`, `models.`) and put every one of them in the task's regression ACs — or just run all suites that source emit.sh.
- When fixing such a fixture, move it to a value that isolates the original assertion (here claude-haiku-5-5, distinct from both light and frontier) rather than loosening the asserted warning count, and comment why.
- Attribute cross-task regressions with a detached `git worktree add --detach <tmp> HEAD` run before assigning the fix.
