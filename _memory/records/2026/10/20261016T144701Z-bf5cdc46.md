Pitfall: structural guard anchors and their mutation proofs can both be non-discriminating when the anchor phrase also appears elsewhere in the file.

What happened (agent-kit goal orchestration-ready-groups): three times a grep anchor in a new guard script passed for the wrong reason. (1) A "file-tree entry" check grepped `ready-groups.md`, which prose elsewhere in ORCHESTRATION.md already contained — removing the file-tree entries still passed. (2) A "lost-report exception" check grepped `report lost, files`, a phrase also present in the Silent-success section. (3) The orchestrator's own mutation proof for (2) used `sed '/report lost, files/d'`, which deleted both occurrences, so the "proof" failed for the wrong reason and hid the weak anchor.

How detected: task and audit evaluators counted the anchor's occurrences with Grep and noticed it matched lines outside the rule it claimed to lock.

Avoid it: pick anchors that occur exactly once and only inside the rule being locked (check with `grep -c` → 1), e.g. `preflight.md,ready-groups.md,` for the tree line or `whose paths are matched by fence alone` for the exception. In mutation proofs delete only the targeted line (anchor on the unique phrase) and print the count of any shared phrase left behind, so the proof shows the guard fails because the rule is missing.
