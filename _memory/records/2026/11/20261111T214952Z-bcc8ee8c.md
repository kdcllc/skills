Decision (2026-11-11, user request during pull request #14): in kdcllc/skills a pull request that changes a skill's folder carries that skill's release preparation itself — the new metadata.version in SKILL.md and a dated "## [X.Y.Z] - YYYY-MM-DD" heading under an empty "## [Unreleased]" in its CHANGELOG.md — and names the versions in the pull request description. This replaced the earlier rule that only agent-kit bumped inside the pull request and other skills were bumped by scripts/release-skill.sh after the merge. The rule is in AGENTS.md § Versioning rules and CONTRIBUTING.md § Release steps.

Tags. .github/workflows/tag-on-merge.yml runs scripts/tag-released-skills.sh on pushes to master that touch skills/, pushes a tag <name>/vX.Y.Z for every recorded version without one, and starts release.yml per tag with gh workflow run --ref <tag>, because a tag pushed with the workflow token triggers no workflow. release.yml refuses a ref that is not a tag. scripts/release-skill.sh is the manual fallback (it only validates and tags when the version is already recorded, and stops when the tag exists). tests/release/run.sh covers the tagging script.

Remember next time. After a bump, skill-status.sh prints "record changes under Unreleased" for a correctly prepared skill; that is expected. After an agent-kit bump, re-run scripts/agent-kit/self-install.sh before the full suite, because cursor-isolation.sh compares the dogfood instance's kit version with metadata.version. Not enforced by CI yet; the published skill-versioning and terraform-azure texts still describe the old flow. The workflow's first real run was to be the merge of pull request #14 — check there whether the workflow token could push the tags.
