What went wrong. Two plan-level slips repeated a known pattern (a check tightened in one task without the matching obligation in the producer task). (1) Task 04 made the suite run the guard under macOS /bin/bash 3.2, but the guard task had no bash 3.2 requirement. (2) The guard task required "only bash, grep and awk" and "POSIX options", while two lines it was told to keep unchanged used `dirname` and `grep -r`; the task evaluator returned NEEDS FIXES on lines that predated the goal.

How it was detected. The Phase 3 evaluator on attempt 2 (after the consumer-side change was added in a revision), and the task 03 evaluator reading the requirement by its letter.

How to avoid it. When a revision adds a requirement on a consumer (a test or CI leg), re-read every producer task for the matching obligation in the same revision. When a requirement states a tool or portability allow-list for a whole file, grep the existing file for violations at planning time and either scope the requirement to new code or list the existing lines to change. A content-inspecting grep criterion whose pattern contains `$` needs `grep -F`; an unquoted-regex `$` silently matches nothing.
