Pitfall: bumping the kit version inside a goal breaks every kitVersion reader until the dogfood instance is re-emitted, and an amendment that adds a release bump is material, not additive.

What happened (goal regression-proof-resume): after the audit, the user asked for a release, and corrective tasks 06a (QA fixes plus metadata.version 2.3.0) and 06b (tests plus goldens) were added. The orchestrator first classified the amendment as additive. The Phase 3 evaluator rejected that: the amendment changed the version that tests and the manifest read, which is a material amendment (full pre-flight, fresh Phase 3, attempt count reset). The re-run found that tests/agent-kit/checks.sh check J compares the root manifest's kitVersion (written by self-install) with metadata.version. Workers may not self-install, so 06b's rung-2 "checks rc=0" criterion could not be met. A repo search for `metadata\.version|kitVersion` in tests, scripts and skills/agent-kit/bin found 74 hits and 14 reader files that needed Consumer rows.

How detected: the Phase 3 evaluator traced the version readers, and a blind consumer-trace pass added .github/workflows/release.yml.

Avoid it: treat any version bump as a material amendment. Search the kitVersion and metadata.version readers before writing tasks. Put an explicit "orchestrator runs scripts/agent-kit/self-install.sh (logged) right after the bump task passes" step into goal.md Constraints, and tell the bump task's evaluator that check J failing before that step is expected. Regenerate goldens (emit-golden.sh --update) only after the bump, in the test task.
