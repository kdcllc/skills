Pitfall: applying an evaluator's optional recommendation to one task file can create a new cross-task defect.

What happened. During goal evaluation of orchestration-advisor (2026-11-10), the evaluator recommended, but did not require, that the guard task match signal keys as whole words in a specific shape: backticked in a table row of the contract file and followed by an equals sign in the script. The orchestrator applied it to the guard task only. The next evaluation failed: the two producer tasks were never told to write that shape, so a script printing keys through a helper would have met its own task and then failed the guard, and the guard task was forbidden from editing the skill.

How it was detected. The resumed evaluator traced the new guard rule back to its producers and found neither stated the shape.

How to avoid it. When a revision tightens what a consumer task checks, add the matching requirement to every producer task in the same edit, or leave the recommendation as a follow-up. Treat a tightened check as an interface change, not a local edit.

A second, related observation from the same goal: a search pattern for a registry file name matched 96 golden test fixtures that merely mention the file in prose. Excluding the fixture tree from that search kept the consumer table usable.
