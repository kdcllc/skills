Pitfall: a feature branch created from a stale local master hid upstream tooling that the plan's acceptance criteria depended on.

What happened. The goal branch was created from local master, eight commits behind origin/master. Upstream had added scripts/check-skill-versions.sh and a "release prepared" status in skill-status.sh. Pre-flight flagged the missing script and the plan was edited around it; later the release task failed its skill-status criterion for the same reason.

How it was detected. The release-task implementer traced the failing criterion to the absence of a release-prepared branch in skill-status.sh; the orchestrator then compared HEAD with origin/master (git fetch; git rev-list --count HEAD..origin/master).

How to avoid it. Run git fetch and compare the base with origin before creating a goal branch, and branch from origin/<default>. If the base is stale mid-goal, move uncommitted work with stash, reset to origin, pop, after the in-flight writers finish and before evaluators run; record a hash baseline first so fence checks still work after the move resets mtimes.
