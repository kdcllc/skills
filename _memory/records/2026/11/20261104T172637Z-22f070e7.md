Pitfall: plain `git config` inside a linked worktree writes the main repository's shared `.git/config`.

What happened (2026-11-03): a subagent needed scratch merges and ran `git worktree add -q --detach $T HEAD; cd $T; git config user.email t@t; git config user.name t`. Worktrees share `config` with the main repo, so `[user] t <t@t>` was appended to the real config. Later work in any worktree of that repo committed as `t <t@t>`, which took a user-approved history rewrite to clean up.

How it was detected: `git config --show-origin --get-regexp '^user\.'` showed a local identity. Grepping session transcripts for `t@t` and comparing their mtimes with the config change found the command. A throwaway-clone reproduction confirmed that only this command shape writes exactly that value with no stray commits.

Avoid it:
- For scratch repos, use `git clone` or `git archive | tar -x` into a temp dir, not `git worktree add` on the real repo.
- Set identity per command (`git -c user.email=… -c user.name=…`) or with GIT_AUTHOR_*/GIT_COMMITTER_* env. Never run `git config user.*` in any checkout of a real repo.
- After every subagent, compare `git config --local --get-regexp '^user\.'` (ORCHESTRATION repository safety) and stop on any change.
- Kit test suites now enforce this for fixtures: fixture-root.sh scrubs git env, and `assert_fixture_repo` rejects linked-worktree roots.
